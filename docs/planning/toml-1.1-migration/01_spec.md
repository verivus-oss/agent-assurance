# Spec — TOML 1.0 → TOML 1.1 migration of the validator/conformance stack

Status: **U01/U02 complete — parity decision GO (2026-06-08), operator
sign-off confirmed; cleared for U03+**
Created: 2026-06-08
Referenced by: [`implementation-dag.toml`](implementation-dag.toml) `[meta].spec`

## 1. Motivation

Dependabot surfaced `toml 1.1.2+spec-1.1.0` for the Rust tooling, and PR
#1 already merged it into `tools/dagtoml-rdf`. That crate implements
**TOML 1.1**, which accepts inputs the **TOML 1.0** conformance corpus
marks invalid — e.g. seconds-less local times (`17:45`) and `\x` hex
escapes (`"\x33"`). The decision was taken to adopt TOML 1.1
**deliberately**, as a spec-semantics change, rather than letting it
arrive piecemeal through dependency bumps.

This document is the normative scope of that migration.

## 2. The load-bearing constraint: cross-implementation parity

The repo's foundational invariant (CONTRIBUTING.md, the conformance
suite) is that the **primary normative implementations agree byte-for-byte
on every fixture**. Today those parsers are split across TOML versions:

| Primary | Parser | TOML version today |
|---|---|---|
| Rust validator | `toml` crate | 1.0 (`0.8`); a 1.1 line (`1.1.x+spec-1.1.0`) exists and is already used by `dagtoml-rdf` |
| Go validator | `BurntSushi/toml` | **1.1 at runtime** — `v1.6.0` (1.1 default) is already required by `go.mod` (via #5); but the conformance *evidence* + harness are still 1.0-era (decoder `v1.4.0`). See U01. |
| Python reference | stdlib `tomllib` | **1.0 only** (stdlib; cannot reach 1.1 without an external parser) |

**Adopting 1.1 in one parser while the others stay 1.0 would
manufacture exactly the divergence the conformance suite exists to
catch — and that split is already latent here:** a document using `17:45`
is *already* accepted by the Go validator's runtime parser (BurntSushi
`v1.6.0`) yet rejected by the Rust validator (`toml` 0.8) and Python
`tomllib`. The conformance harness has not caught it only because its
*evidence* is still generated by 1.0-era tooling (U01). Therefore TOML
1.1 may be adopted **only if all three primaries can reach 1.1 in
lockstep**, and the harness flipped to prove it (U06).

## 3. Normative requirements

- **R1 (parity).** Post-migration, Rust, Go, and Python MUST produce
  identical accept/reject verdicts on the full toml-test 1.1 corpus and
  the dagtoml conformance corpus. (Contract C01.)
- **R2 (gate precedes bump).** No parser may be bumped to 1.1 until a
  recorded go/no-go decision confirms a 1.1-capable parser exists for
  **all three** primaries. If any cannot, the migration halts. (Contract
  C04; readiness gate G02.)
- **R3 (backward compatibility).** Every document valid under TOML 1.0
  before the migration MUST remain valid after, unless a breaking
  1.0→1.1 change is enumerated and justified. (Contract C02.)
- **R4 (explicit feature disposition).** Each TOML 1.1 feature that
  newly becomes parseable MUST be explicitly permitted or forbidden by
  `spec.md` before the harness is flipped. No feature enters the
  conforming surface by parser default alone. (Contract C03.)
- **R5 (safe-tools preserved).** Any new Go/Rust parser dependency MUST
  preserve the `#![forbid(unsafe_code)]` / no-`unsafe` safe-tools policy.

## 4. Out of scope

- Authoring net-new spec features that merely *use* TOML 1.1 syntax. This
  migration changes which parser version the stack conforms to; it does
  not redesign any document kind.
- The cosmetic `toml-test-decode-rs` bump (PR #4) in isolation — it is
  folded in here as unit U06, gated behind the parity decision.

## 5. Success criteria

The migration is complete when unit U08 records that rs/go/py agree on
the full TOML 1.1 corpus with an empty known-divergences baseline, and
`spec.md` carries an explicit permit/forbid disposition for every 1.1
feature. If the parity decision (U02) is NO-GO, the migration is
"complete" in the negative sense: the blocker is recorded, no parser
changes land, and the repo remains uniformly TOML 1.0.

## 6. Open questions (resolved by U01/U02)

3. Are there 1.0→1.1 breaking changes that affect any existing repo
