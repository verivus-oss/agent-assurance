# U01 — Parser-availability survey (TOML 1.1)

Status: **complete**
Unit: [`implementation-dag.toml`](../implementation-dag.toml) `units.U01`
Produces: `ART:parser-availability-survey`
Created: 2026-06-08

This is the pure-research deliverable that the parity go/no-go decision
(U02, [`02-parity-decision.md`](02-parity-decision.md)) consumes. It
surveys whether a TOML **1.1**-capable parser exists for each of the
three primaries — Rust, Go, Python — and the conformance harness, and
records each candidate's default-version behaviour, safe-tools posture,
and pinning mechanism.

## Headline

TOML **1.1.0 is a finalized, released specification** — not a draft. The
toml-lang/toml `1.1.0` GitHub release tag is dated **2025-12-24**
(`published_at: 2025-12-24T17:30:07Z`); the human-readable spec page at
<https://toml.io/en/v1.1.0> carries a "Published on 12/18/2025" line. The
two dates refer to different artifacts (the GitHub release vs. the spec
page); the binding fact is that 1.1.0 is released, not draft. (Note:
**2025-12-18** is separately the date of the BurntSushi/toml v1.6.0 and
the Rust `toml` 0.9.10 releases that shipped 1.1-by-default — do not
conflate it with the spec tag.) A 1.1-capable parser exists, and
parses 1.1 **by default**, for **all three primaries** and for the
`toml-test` conformance harness. Two of the three Rust/Go parser moves
have, in fact, *already landed silently via dependency bumps* (see
"Current repo state" below), which is the latent divergence this
migration exists to resolve deliberately.

## Per-primary findings

### Rust — `dagtoml-validate-rs` and `toml-test-decode-rs`

| Field | Finding |
|---|---|
| Parser today | `toml` crate `0.8` (`tools/dagtoml-validate-rs/Cargo.toml`, `tools/toml-test-decode-rs/Cargo.toml`), parse-only features — TOML **1.0** |
| 1.1-capable line | `toml` `0.9.10` (released **2025-12-18**) first added TOML 1.1 parse support; current release `1.1.2+spec-1.1.0` (2026-04-01). The `+spec-1.1.0` build metadata denotes the implemented spec level. |
| Default at parse? | **Yes** — `toml` 0.9.10 changelog lists 1.1 parsing (multi-line inline tables, trailing commas, `\e` and `\xHH` escapes, optional seconds) under *Features* with no opt-in flag. |
| Safe-tools (R5) | Our crates already carry the no-`unsafe` posture; the `toml`/`toml_edit`/`winnow` stack is pure Rust. The 1.1 line is **already vendored and proven in-repo**: `tools/dagtoml-rdf/Cargo.toml` pins `toml = "1.1"` (landed via PR #1). |
| Pin mechanism | Cargo semver requirement + `Cargo.lock` exact pin + the existing Rust license/ban CI gate. |

**Conclusion:** Rust 1.1 is proven. U03 is a `0.8 → 1.1` bump of
`dagtoml-validate-rs` (and the `toml-test-decode-rs` shim) mirroring the
line already used by `dagtoml-rdf`.

### Go — `dagtoml-validate-go`

| Field | Finding |
|---|---|
| Parser today | `github.com/BurntSushi/toml` **v1.6.0** is already required by `tools/dagtoml-validate-go/go.mod` (landed via PR #5, "deps(gomod): Bump github.com/BurntSushi/toml"). |
| 1.1 support | BurntSushi/toml added opt-in 1.1 behind the `BURNTSUSHI_TOML_110` environment variable in **v1.3.0** (2025-05-30), then **made TOML 1.1 the default in v1.6.0** (2025-12-18): the v1.6.0 release notes state *"TOML 1.1 is now enabled by default."* |
| Default at parse? | **Yes, unconditionally.** Verified against the vendored source at `$GOMODCACHE/github.com/!burnt!sushi/toml@v1.6.0`: the `BURNTSUSHI_TOML_110` / `tomlNext` env-var gate is **gone** in v1.6.0 — there is no toggle; 1.1 is the only behaviour. |
| Safe-tools (R5) | **Verified pure Go.** The vendored v1.6.0 source contains **no `import "unsafe"`** and **no cgo (`import "C"`)**. BurntSushi/toml is reflection-based pure Go. Satisfies the no-`unsafe` safe-tools policy with no exception. |
| Pin mechanism | `go.mod` require + `go.sum` content hash (`h1:dRaEfpa2VI55EwlIW72hMRHdWouJeRF7TPYhI+AUQjk=`). |

**Conclusion:** Go 1.1 is not merely available — it is **already linked
by the Go validator at runtime** (v1.6.0, 1.1-default). The Go parser
"move" (U04) is therefore primarily a *conformance-and-pinning*
exercise: the runtime parser is 1.1, but the conformance evidence is
still generated by the older v1.4.0 decoder (see "Current repo state").
This unit, previously assessed as the highest-risk of the three, is
**de-risked** by the released, no-`unsafe`, default-1.1 v1.6.0.

### Python — reference validators (`validators/*.py`)

| Field | Finding |
|---|---|
| Parser today | stdlib `tomllib` (PEP 680), used across ~13 validators (`validate_closure_root.py`, `validate_implementation_dag.py`, `validate_review_readiness.py`, `validate_kind_descriptor.py`, …). `tomllib` is **TOML 1.0 only** and tracks the stdlib release; it cannot reach 1.1 without an external parser. |
| 1.1-capable replacement | **`tomli` 2.4.0+** (PyPI). Changelog 2.4.0: *"TOML v1.1.0 compatibility."* `tomli` is the **upstream project from which stdlib `tomllib` was derived** (PEP 680; same author, hukkin), so it is the lowest-surprise, highest-trust drop-in: `tomllib.load(f)` → `tomli.load(f)` with an identical API. |
| Default at parse? | **Yes** — "Version 2.4.0 and later are compatible with TOML v1.1.0; older versions are TOML v1.0.0 compatible." There is no per-call spec flag; the installed version's default *is* 1.1. This matches the rs/go default-1.1 behaviour required for parity. |
| Safe-tools / supply chain | Pure-Python wheel (`tomli-2.4.x-py3-none-any.whl`) is published on every platform (mypyc binary wheels are an optional perf build only; the `py3-none-any` wheel is pure Python). Zero dependencies. Supports Python ≥3.8. Same maintainer and provenance as the stdlib module it replaces — the strongest possible trust posture for a `tomllib` substitute. |
| Pin mechanism | Hash-pinned `requirements/toml.txt` (`tomli==2.4.x --hash=sha256:…`, forcing the `py3-none-any` pure-Python wheel). |

**Conclusion:** Python 1.1 is available with an exceptionally clean trust
story — the replacement is the parent of the stdlib module. U05 swaps
`import tomllib` for a thin `tomli`-or-`tomllib` shim and pins `tomli`.

> Open question O2 from the spec ("trust posture of the candidate Python
> 1.1 parser") is **answered favourably**: `tomli` is not a third-party
> risk so much as the un-vendored original of the very stdlib dependency
> being replaced.

### Conformance harness — `toml-lang/toml-test`

| Field | Finding |
|---|---|
| Pinned today | `TOML_TEST_VERSION := v1.6.0` (the toml-test runner) and `TOML_TEST_DECODER_VERSION := v1.4.0` (the BurntSushi decoder binary) in the `Makefile` — both **TOML 1.0**-era. |
| 1.1 support | `toml-test` **2.0.0** sets TOML 1.1 as the default test version and adds `-toml 1.0` / `-toml 1.1` selection; `version.go` on `main` declares both `1.0.0` and `1.1.0`, each with its own `exclude` set. The 1.1 set drops the cases that are no longer invalid (times without seconds, `\x` escape, trailing commas in inline tables). |
| U06 action | Bump `TOML_TEST_VERSION` to a 1.1-capable release, invoke with `-toml 1.1.0`, and regenerate the Go/Rust decoder evidence from the **1.1** parsers (BurntSushi v1.6.0 decoder + the bumped `toml-test-decode-rs`). |

## Current repo state — the latent divergence (key finding)

The migration's premise is already partially, silently true:

| Surface | Parser | TOML version **right now** |
|---|---|---|
| `dagtoml-validate-go` (runtime) | BurntSushi/toml **v1.6.0** | **1.1** (default) — via PR #5 |
| `dagtoml-rdf` (reference tooling) | `toml` **1.1** | **1.1** — via PR #1 |
| `dagtoml-validate-rs` (runtime, primary) | `toml` **0.8** | **1.0** |
| `toml-test-decode-rs` (rs conformance shim) | `toml` **0.8** | **1.0** |
| Python reference validators | stdlib `tomllib` | **1.0** |
| Go conformance evidence (`toml-test-decoder`) | BurntSushi **v1.4.0** | **1.0**-era |
| `toml-test` runner | **v1.6.0**, run without `-toml 1.1.0` | **1.0** corpus |

So the Go **validator** already parses 1.1 at runtime, while its
**conformance evidence** is generated by a 1.0-era decoder and the Rust
and Python primaries are still 1.0. This is exactly the
"1.1 arriving piecemeal through dependency bumps" condition the spec
(§1) names. Two of the three parser bumps have de facto happened; the
migration's job is to make the move **deliberate, complete, and proven**
rather than partial and unverified.

## Backward-compatibility note (feeds R3 / C02)

Every TOML 1.1 change relative to 1.0 is a **relaxation** (superset), not
a removal or redefinition:

- multi-line inline tables, trailing commas in inline tables;
- optional seconds in local/offset times (`17:45`);
- `\e` (ESC) and `\xHH` hex string escapes.

No 1.0 construct is removed or given new meaning. Therefore **every
existing TOML 1.0-valid document in the repo remains valid under 1.1** —
no enumerated breaking change affects any repo document. The only
direction of change is that **9 inputs the 1.0 corpus marks *invalid*
become *valid* under 1.1** (e.g. `17:45`, `"\x33"`); those are
handled by flipping the harness to the 1.1 corpus (U06), not by any
change to repo documents. Per-feature *spec* disposition (permit/forbid)
is the separate concern of U07 (R4/C03).
